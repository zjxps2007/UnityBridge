# RC1 이후 속도 개선 검증

한국어 | [English](SPEED_FOLLOWUP.md)

이 변경은 **v0.3.0-rc.2에 포함**합니다. 측정은 RC2 버전 변경 전에
`codex/external-host-compiler`의 `5945c3b` (`v0.3.0-rc.1`) 이후 작업 내용으로
수행했으며 원자료의 당시 버전과 해시는 유지합니다. 자동 업데이트 코드·확인 주기·
동기 네트워크 동작·설치 및 업데이트 대상은 그대로입니다.

## 적용 내용

- CLI: 공개 export와 선택 기능 모듈을 필요할 때 로드하고 선택한 명령의 parser만 생성·캐시합니다.
- 호스트: 인증한 상태 변경 알림으로 탐색을 즉시 깨웁니다. 주기 탐색도 유지하며 포트가 바뀌면 실제 Heartbeat 파일을 다시 확인합니다.
- 완료 대기: 작업별 기록을 리로드 이후에도 유지해 refresh·reserialize·재생·정지의 실제 완료를 확인합니다. 기록 유실·취소 시 변경 명령을 재실행하지 않습니다. 코드 import가 불명확하면 기존 대기를 유지합니다. 상태 조회는 한 번에 최대 1초만 기다리고 일시적인 리로드 거부를 재시도하며 전체 대기 제한을 지킵니다.
- 컴파일러: ReadyToRun 빌드로 최초 JIT 작업을 줄였습니다. 비교용 `--no-ready-to-run`도 제공합니다.
- 연속 호출: 선택 기능인 JSONL `session`이 CLI 프로세스를 유지합니다. Unity는 요청마다 다시 찾고 명령도 매번 실행합니다.
- 캐시: 여러 컴파일이 공유하는 참조 이미지의 메모리를 한 번만 계산합니다. 같은 경로·MVID의 이미지를 다시 읽었고 이전 이미지가 남아 있다면 각각 계산합니다. 매 요청의 MVID 검사와 실행별 고유 assembly identity는 유지합니다.

## 같은 조건의 응답 시간

Windows, Python 3.14.4 / PyInstaller 6.20.0, .NET SDK 10.0.401 / Roslyn 5.0.0입니다.
양쪽 모두 독립 호스트를 사용했습니다. Unity 버전별로 새로운 빈 프로젝트에서
이전→개선→개선→이전 순서로 측정했습니다. 일반 명령은 버전·변형별 80회,
각 exec 종류는 40회, 변경 없는 refresh 대기는 16회입니다. 백분위는 nearest-rank로
계산했습니다. 단위는 ms이며 **작을수록 빠릅니다**.

| 명령 | Unity 2021: RC1 → 개선본 (p50 / p95) | Unity 6: RC1 → 개선본 (p50 / p95) |
|---|---:|---:|
| status | 86.7 / 90.7 → 68.0 / 71.3 | 86.7 / 89.5 → 68.1 / 70.7 |
| console | 106.8 / 121.8 → 103.6 / 119.9 | 109.8 / 120.1 → 103.2 / 119.8 |
| tools | 109.2 / 124.9 → 109.2 / 112.9 | 109.9 / 125.0 → 108.9 / 123.2 |
| exec: 서로 다른 코드 | 124.2 / 143.2 → 110.7 / 139.9 | 125.5 / 142.9 → 116.7 / 142.0 |
| exec: 같은 코드 반복 | 123.0 / 140.1 → 109.4 / 141.6 | 123.0 / 141.1 → 118.1 / 140.6 |
| refresh --wait: 변경 없음 | 1614.3 / 1628.1 → 155.9 / 529.8 | 1617.9 / 1627.7 → 143.4 / 181.8 |

두 Editor 모두 status·console·tools p95 저하 한도 `기존 p95의 5% 또는 10ms 중 큰 값`을
통과했습니다. 모든 개별 요청이나 exec 백분위가 빨라졌다는 뜻은 아닙니다.
변경 없는 refresh는 완료 확인 비용을 측정한 것으로, 대규모 asset import나 실제
스크립트 컴파일 자체가 같은 비율로 빨라지는 것은 아닙니다.

## 세션과 첫 실행

| Unity | 매번 실행한 console p50 / p95 | 세션 console p50 / p95 | 세션 첫 명령, 2회 |
|---|---:|---:|---:|
| 2021.3.19f1 | 103.6 / 119.9 | 15.9 / 31.6 | 97.3–126.7 |
| 6000.3.13f1 | 103.2 / 119.8 | 16.8 / 31.9 | 99.7–113.6 |

세션 후속 명령은 프로세스 시작 비용을 제외한 40회 측정입니다. `session`을 열어 두어야
이 이득을 얻으며 일반 CLI를 매번 다시 실행하면 해당 비용을 계속 냅니다.
세션 요청은 기존 JSON 출력의 업데이트 알림 생략 규칙을 따릅니다. 자동 업데이트를
다른 프로세스로 옮기지 않았습니다.

| Unity | RC1 서비스 시작부터 첫 exec 결과 | 개선본 |
|---|---:|---:|
| 2021.3.19f1 | 776.3–782.9 | 497.5–501.9 |
| 6000.3.13f1 | 855.6–867.0 | 545.5–602.2 |

서비스 첫 시작은 변형마다 **2회뿐이므로 범위로 제시**했습니다. 신뢰할 만한 p95로
일반화할 수 없습니다. 실행 중인 OS에서 프로세스를 새로 시작한 값이며 설치 직후나
재부팅 직후의 측정은 아닙니다. 이 항목은 사전 준비 완료를 기다리지 않고 첫 명령을 보내며, 준비된 일반 명령 및
사전 준비만 끝낸 첫 호출은 원자료에서 따로 구분합니다.

## 컴파일러·캐시와 비용

같은 최종 소스의 JIT/R2R 워커를 각각 12개씩 순서를 번갈아 새로 시작하고 Unity 6의
실제 참조 집합으로 비교했습니다. 시작부터 첫 컴파일까지 p50은
**586.9 → 314.2ms**,
ping 이후 첫 컴파일은 **516.0 → 245.8ms**,
그다음 컴파일은 **12.4 → 12.5ms**였습니다.
Unity 실행을 제외한 컴파일러 구성 요소의 시간입니다. 첫 JIT 표본에는 큰 이상치가
있어 원자료를 보존했습니다. ReadyToRun은 초기 JIT 비용을 줄이는 대신 코드 용량을
늘립니다. Native AOT가 아니며 .NET 런타임을 계속 동봉합니다.
[Microsoft ReadyToRun 문서](https://learn.microsoft.com/en-us/dotnet/core/deploying/ready-to-run)

8종 코드를 순환 실행한 두 번째 순회에서는 두 Editor 모두 캐시 적중이
**0/16 → 16/16**으로 늘었습니다. 준비 정보의 재사용이며 실행 결과 재사용이 아닙니다.
정적 카운터는 매 호출 1에서 시작함을 검증했습니다. 컴파일 항목 64개와 추정 유지
용량 256 MiB 제한은 그대로이며 실제 프로세스 메모리 상한은 아닙니다.

Windows 설치 용량은 **113.2 → 129.2 MiB**,
ZIP은 **50.1 → 57.8 MiB**입니다.
설치할 때 한 번 압축을 푸는 방식은 같습니다. 실행 후 working set은 변형별 두 번
측정했습니다.

| Unity | 프로세스 | RC1 MiB | 개선본 MiB |
|---|---|---:|---:|
| 2021.3.19f1 | Unity | 296.6–297.6 | 297.4–303.0 |
| 2021.3.19f1 | Host | 33.9–33.9 | 34.0–34.0 |
| 2021.3.19f1 | 컴파일러 | 194.8–196.7 | 199.0–199.4 |
| 6000.3.13f1 | Unity | 433.8–441.6 | 433.9–440.0 |
| 6000.3.13f1 | Host | 34.0–34.1 | 34.1–34.2 |
| 6000.3.13f1 | 컴파일러 | 209.3–213.9 | 212.9–214.2 |

exec 중 Editor update 간격 p95: unity6: 5.36 → 5.32 ms; unity2021: 6.11 → 6.04 ms.
1ms를 넘는 간격만 기록했습니다. GUI 프레임 시간·최대 메모리·장시간 assembly 누적의
측정은 아닙니다. 준비 정보와 R2R 코드를 유지하면서 워커 메모리는 늘 수 있습니다.
워커 캐시에서 지워도 Unity에 로드한 assembly가 unload되는 것은 아닙니다.

## 검증 범위

- Python 182개: 181개 통과, Windows 심볼릭 링크 권한 때문에 1개 생략.
- 컴파일러 회귀 15개 통과: 참조 교체, 다시 읽은 이미지의 별도 계산, 캐시 퇴출, 실행별 assembly 분리를 포함합니다.
- Windows ZIP을 새 경로에 풀어 동봉 컴파일러 ping과 JSONL 연속 요청 2개도 통과했습니다.
- 최종 패키지 실제 검증: Unity 2021.3.19f1 16/16, Unity 6000.3.13f1 16/16.
  변경 없는 명시적 컴파일, 실제 리로드 후 작업 완료, 재생·정지 대기, 세션,
  인증, listener 교체, 만료된 요청의 실행 방지, 정적 상태 격리, 컴파일 실패 복구를 확인했습니다.
- 강화한 검증에서 이전 listener의 읽기 대기와 리로드 중 일시적 거부를 발견해 수정했습니다.
  재시도는 상태 확인에만 적용하며 변경 명령은 한 번만 전달합니다.
- 5개 플랫폼 릴리스 CI에 JSONL 세션 검증과 R2R 빌드를 반영했습니다. 이번 작업에서 Linux/macOS CI 실행이나 배포는 하지 않았습니다.
- Unity 2020.3 실제 실행, 대형 프로젝트, GUI·백그라운드 창, 재부팅 직후,
  에이전트 요청부터 답변 표시까지의 시간은 미측정입니다. 속도 비교 시 양쪽 모두
  업데이트 확인을 껐으므로 해당 네트워크 지연은 수치에 포함하지 않습니다.

[원자료·판정·소스 해시](SPEED_FOLLOWUP_BENCHMARK.json)에 측정한 작업 내용을 기록했습니다.
같은 환경의 이전·개선 실행 파일로 `scripts/benchmark-host.py --baseline-ref 5945c3b
--baseline-host --extended`를 실행하고, 기능은 `scripts/verify-host.py`로 재현합니다.
`scripts/benchmark-worker.py`는 저장된 `compiler-context.json`, `--jit`, `--r2r`,
새 출력 파일을 받으며 참조 DLL이 해당 경로에 남아 있어야 합니다.
[실제 Unity 검증 방법](../tests/unity/README.md)도 참고하세요.
