# Python 첫 응답 및 명령 속도 개선

한국어 | [English](PYTHON_STARTUP.md) | [README](../README.ko.md)

공개 **v0.3.0-rc.2 이후 개발 변경**입니다. 공개 RC2 파일이나 정식 v0.2.3을
변경하지 않습니다. CLI와 호스트는 Python, 컴파일러는 별도 Roslyn 프로세스를
유지합니다. Python 패키지의 최소 지원 버전도 3.10입니다.

## 구현 내용

- Connector 초기화 때 파일 확인과 외부 호스트 시작을 백그라운드로 예약합니다.
  에셋 import worker는 제외합니다. 앞당기는 것은 외부 프로세스 준비이며,
  Unity 참조 수집과 실제 실행은 준비 상태 확인 이후에 수행합니다. 호스트가
  살아 있다는 이유로 Unity를 ready로 표시하지 않습니다.
  [Unity 초기화 제약](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/InitializeOnLoadAttribute.html)
- `_host` 진입점을 분리하고 서버 모듈 import와 컴파일러 프로세스 시작을
  겹칩니다. 준비된 프로젝트가 없으면 Unity 참조가 필요 없는 작은 코드를
  컴파일한 뒤 결과를 버립니다. 이 코드는 실행하지 않습니다. 실제 요청은
  아직 시작하지 않은 사전 준비보다 우선하며, 이미 진행 중인 컴파일을
  강제로 중단하지는 않습니다.
- 처음 발견한 Connector가 아직 참조를 준비 중이면 첫 요청을 원래 제한 시간
  안에서 대기시킵니다. 이때 상태 조회는 참조 준비를 기다리지 않습니다. 대기 중
  만료된 요청은 준비가 끝난 뒤에도 실행하지 않습니다. Unity 시작 반복 검증에서
  찾은 초기 협상 경쟁 상태를 수정한 내용입니다.
- `exec`의 경량 경로를 `console`, `tools`, `wait-ready`로 확대합니다.
  호스트의 지원 명령 목록으로 구버전 호환성을 판별합니다. 지원하지 않는
  문법과 컴파일러 직접 지정 옵션은 전송 전에 기존 경로를 선택합니다.
  자동 업데이트의 확인 주기와 동작은 그대로입니다.
- `instances`와 `status`의 경량 전달도 구현했지만, 첫 Windows 비교에서 p95가
  허용 범위를 넘었습니다. 기본값은 기존 로컬 처리이며
  `UNITY_BRIDGE_FAST_SNAPSHOTS=1`로만 해당 실험 경로를 활성화합니다.
- 세션은 결과 객체를 바로 받아 JSONL로 한 번 직렬화합니다. 일반 CLI의 출력
  문자열을 다시 JSON으로 읽거나 프로세스 전체 stdout을 바꾸지 않습니다.
  JSONL 형식과 요청별 Unity 탐색 의미는 유지합니다.
- 장기 실행 클라이언트와 호스트는 제한된 수의 HTTP 연결을 재사용합니다.
  실행·상태 확인·참조 협상 연결을 분리하고 PID·포트·도메인·참조 세대·호스트
  identity가 바뀌면 해당 연결을 폐기합니다. 응답은 끝까지 읽습니다. 새 요청을
  쓰기 전에 닫힌 유휴 연결을 교체할 수 있지만, 이미 전송한 요청의 응답이
  유실되면 자동 재실행하지 않습니다.
  [Python HTTP 연결 재사용](https://docs.python.org/3.14/library/http.client.html)
- 기본 Compilation과 코드별 Compilation은 기존 64개·추정 256MiB 보존 예산을
  함께 사용합니다. 프로젝트·컴파일러·참조·언어·옵션을 키에 포함하며 매 요청의
  MVID 검증과 고유 assembly identity를 유지합니다. Roslyn이 관측한 메타데이터는
  파생 구성으로 전달할 수 있지만, assembly 이름 변경 시 심볼 바인딩을 다시
  해야 하므로 준비 비용 전체가 사라지는 것은 아닙니다. 실행 결과나 로드된
  Assembly는 재사용하지 않습니다. 이 캐시는 별도 측정에서 이득이 없어
  기본값에서는 끄고 `UNITY_BRIDGE_ENABLE_BASE_COMPILATION=1` 실험 옵션으로
  남깁니다. 기존 코드별 컴파일 캐시는 계속 사용합니다.
  [Roslyn 실제 구현](https://github.com/dotnet/roslyn/blob/main/src/Compilers/CSharp/Portable/Compilation/CSharpCompilation.cs)
- 호스트·컴파일러·전달 프레임의 제한 시간에는 `perf_counter()`를 사용합니다.
  검증한 Windows Python 3.12는 monotonic 시계 해상도가 15.625ms였고,
  QPC 성능 시계는 0.0001ms였습니다. 탐색이나 잠금 대기 전에 만료 시점을
  고정해 대기 시간이 원래 제한 시간에 다시 더해지지 않도록 수정했습니다.
  [Python 시간 함수 의미](https://docs.python.org/3.12/library/time.html#time.perf_counter)

## 재현 방법과 계측

기준은 공개 RC2 실행 파일입니다. RC2 소스를 로컬 Python 3.14로 빌드한 결과는
공개 기준과 구분합니다. 같은 컴파일러 폴더와 패키징 도구를 사용합니다.

```powershell
python scripts/build-standalone.py --compiler-dir <배포한-워커-폴더> --output-name unity-bridge-windows-amd64.zip --output-dir <변형-출력> --work-dir <변형-빌드>
python scripts/benchmark-host.py --unity-editor <Unity.exe> --unity-version <버전> --baseline-bin <공개-RC2.exe> --candidate-bin <개선.exe> --baseline-ref v0.3.0-rc.2 --baseline-host --variants baseline candidate --cold-samples 50 --samples 100 --exec-samples 100 --session-samples 100 --extended --output <빈-폴더>
```

측정기는 별도 임시 프로젝트와 Unity 프로세스를 만듭니다. 반복 서비스 시작
측정에서는 양쪽 검증용 Connector의 자동 시작만 동일하게 끕니다. 측정 시간은
`_host start` 프로세스, 탐색, 첫 CLI 프로세스와 첫 실행을 포함합니다.
`--startup-host --cold-samples 1`은 Unity 시작 전에 등록하고 ready Heartbeat 직후
첫 명령을 보내는 별도 시나리오입니다. `--gui foreground|background`는 실제로
Unity가 전경 창인지 기록합니다. batchmode의 Editor update 간격은 GUI 정지 시간과
같은 값이 아닙니다.

개별 효과는 `--candidate-env 이름=1`로 실험합니다.
`UNITY_BRIDGE_DISABLE_FAST_CLI`, `UNITY_BRIDGE_DISABLE_CONNECTION_REUSE`,
`UNITY_BRIDGE_DISABLE_BASE_COMPILATION`, `UNITY_BRIDGE_DISABLE_EARLY_HOST`,
`UNITY_BRIDGE_DISABLE_COMPILER_WARMUP`을 제공합니다. 일반 사용에 필요한 설정은
아닙니다. 성능 판정에서는 계측을 끄며 OS 파일 캐시를 비우지 않습니다.
재부팅 직후 성능으로 표현하지 않습니다.

`UNITY_BRIDGE_ENABLE_BASE_COMPILATION=1`은 실험용 기본 Compilation 캐시를 켭니다.
`UNITY_BRIDGE_DISABLE_COMPILER_WARMUP`은 프로젝트 참조 준비 전체가 아닌,
Unity와 무관한 프레임워크 사전 컴파일만 끄는 비교 옵션입니다.

`UNITY_BRIDGE_TIMING_DIR`를 빈 폴더로 지정한 뒤 CLI·호스트·Unity를 시작하면
프로세스별 JSONL을 기록합니다. 진입/import, 컴파일러 시작/요청, 참조 협상,
호스트 대기, Unity 메인 스레드 대기, 실행, 직렬화, 전송을 구분합니다. 코드,
매개변수, 실행 결과, 인증 토큰은 기록하지 않습니다. Python은 나노초,
Unity는 Stopwatch ticks/frequency를 기록합니다. 정확한 구간 길이는 같은
프로세스 안에서 계산하고, epoch 시각은 프로세스 간 대략적인 정렬에만 사용합니다.
Windows의 CLI 프로세스 시작 구간은 부모 측정기와 실행 파일이 공유하는 QPC 시계로
기록합니다. 이 진단 실행에는 프로세스 종료까지의 구간도 포함합니다.
파일 기록이 측정에 영향을 주므로 채택 판정 수치에는 포함하지 않습니다.

## Python 버전 및 배포 방식

최종 RC2 비교는 공개 실행 파일과 `python312.dll` 해시가 같은 공식
**CPython 3.12.10**을 사용합니다. 별도 런타임 실험은 표준 CPython
3.12.13·3.14.5, 패키징 실험은 양쪽 모두 3.12.13을 사용했습니다.
이 실험들은 같은 소스, PyInstaller 6.20.0, 같은 .NET 10/Roslyn 워커를
사용하며 Nuitka는 4.2.1입니다. Python 배포본이 다른 비교의 차이를 모두
응용 코드의 효과로 해석하지 않습니다. GIL 해제 빌드·JIT·추가 상주 워커는
사용하지 않습니다.

```powershell
python scripts/build-nuitka-experiment.py --output <빈-실험-폴더> --compiler-dir <배포한-워커-폴더> --c-compiler mingw64
```

Nuitka 스크립트는 정식 배포용 압축 파일이 아닌 실험용 standalone 폴더를 만듭니다.
Nuitka는 실행 파일 옆에 네이티브 라이브러리를 배치합니다. 현재 설치기는
실행 파일 교체 전에 의존성을 준비할 수 있도록 버전별 고정 런타임 폴더를
요구합니다. `sys.frozen`과 다른 실행 환경 판별 및 실제 실행 파일 경로는
처리했지만, 이것만으로 기본 설치·업데이트 형식까지 호환되는 것은 아닙니다.
[Nuitka standalone](https://nuitka.net/user-documentation/user-manual.html),
[실행 환경 판별](https://nuitka.net/user-documentation/tips.html#detecting-nuitka-compilation-at-runtime)

Nuitka 채택 조건은 첫 결과 p50이 `10% 또는 10ms 중 큰 값` 이상 개선되고,
설치·업데이트와 5개 플랫폼 검증을 모두 통과하는 것입니다. 미달하면 PyInstaller를
유지합니다. 일반 명령의 p95는 공개 RC2보다 `5% 또는 10ms 중 큰 값`을 초과해
느려지면 안 됩니다. 첫 결과 p50 20% 개선은 목표이며 보장 수치가 아닙니다.
메모리·설치 용량 증가의 기본 예산은 10%입니다.

## 측정 결과

준비된 명령과 연속 세션은 빨라졌습니다. **이미 실행 중인 Unity에서 서비스를 새로 시작하는 첫 결과의 p50 20% 단축 목표는 달성하지 못했습니다.** Unity 시작 중 사전 준비를 겹치는 효과는 아래 별도 표로 구분합니다. Python 3.12와 PyInstaller를 유지합니다. Windows의 빈 테스트 프로젝트 결과이며 실제 대형 프로젝트나 에이전트·모델의 응답 시간을 뜻하지 않습니다.

[원자료·체크섬·실험 구분](benchmarks/python-startup-2026-09-19/README.md)

**최종 성능 승인 보류:** 정상 결과와 별도로, 전경 새 코드 실행이 약 337ms로 느려진 유효한 두 실행이 있습니다. 같은 바이너리의 후속 재측정에서는 재현되지 않았지만 원인은 확인되지 않았습니다. 아래 개선 수치를 전체 조건의 무회귀 보장으로 해석하지 않습니다. 5개 플랫폼 CI도 서명 문제로 남아 있습니다.

### 공개 RC2와 현재 후보의 batchmode 비교

표의 값은 **p50 / p95, ms**입니다. 서비스 시작은 변형별 50회, 준비된 명령과 세션은 각각 100회입니다. 서비스 시작에는 `_host start`, 탐색, 첫 CLI 프로세스와 실행이 포함됩니다. Unity는 계속 실행 중이며, 계측은 끄고 OS 파일 캐시는 유지했습니다. 재부팅 직후 측정이 아닙니다. 백분위수는 nearest rank입니다.

### Unity 시작 직후 첫 명령

각 변형의 프로젝트를 한 번 import한 뒤 같은 Library로 50회 재시작했습니다. RC2와 개선본을 번갈아 실행했고, ready Heartbeat를 관측한 직후 `exec`를 한 번 보냈습니다. 최초 import 1회씩은 원자료의 `new_project` 항목에 별도로 보존하고 아래 백분위수에서 제외합니다.

| 6 | Unity 시작 → 첫 결과 | 3794.00 / 3959.99 | 3164.25 / 3351.26 |

Unity 6의 기능별 비교도 변형별 재시작 50회입니다. 사전 준비를 끄는 옵션은 프레임워크 초기화만 끄며 프로젝트 참조 준비는 유지합니다.

| 변형 | Unity 시작 → ready 관측 | Unity 시작 → 첫 결과 | ready 관측 → 첫 결과 |

Nuitka 첫 빌드는 C 컴파일러 다운로드를 포함해 60.82초, 캐시가 있는 재빌드는 16.68초였습니다. 공개 RC2의 원래 빌드 시간은 알 수 없으며 깨끗한 환경에서의 동등한 빌드 시간 비교는 아닙니다.

Python 테스트 **212개 통과·권한 의존 심볼릭 링크 테스트 1개 제외**, 컴파일러 **18개 통과**, 최종 실행 파일로 Unity 2021·6 **각 19개 실제 검증 통과**입니다. 대용량 한글·이모지, 정적 상태 격리, 참조 변경, 리로드, 동시 상태 조회, 만료 후 실행 방지, 응답 유실 시 중복 실행 방지를 포함합니다. 실제 Windows 설치기로 신규 설치·재설치·공개 RC2 업그레이드·등록 경로의 호스트 재실행을 확인했습니다. 설치 다운로드만 로컬 파일로 대체했고 사용자 PATH는 바꾸지 않았습니다.

**5개 플랫폼 CI는 아직 완료하지 못했습니다.** 검증 커밋이 기존 전역 `commit.gpgsign=true` 설정의 GPG pinentry 시간 초과로 실패했습니다. 서명을 임의로 생략하지 않았으며 새 코드의 Linux·macOS 실행이나 배포 검증 완료를 주장하지 않습니다. 서명 문제 해결 후 현재 브랜치에서 `release_tag`를 비운 CI를 실행하면 릴리즈 게시 없이 5개 플랫폼 artifact를 검증할 수 있습니다.

계측 전용 실행은 `accepted-timing.json`, 구간별 JSONL과 `timing-summary.json`에 있습니다. CLI 프로세스 시작·Python 진입·import·호스트 준비·참조 협상·컴파일·Unity 대기/실행·직렬화/전달을 나눕니다. 표본이 적고 파일 기록 비용이 있으므로 성능 채택 판정에는 사용하지 않습니다. 컴파일 구간에는 IPC와 참조 검증도 포함되며 겹쳐 실행된 구간을 단순 합산하지 않습니다.

Windows 패키지의 경량 호출 테스트 21개도 최종 실행 파일로 별도 통과했습니다. 소스 Python 테스트와 구분한 패키징 검증입니다.

### 추가 공식 근거

- [Nuitka runtime detection](https://nuitka.net/user-documentation/tips.html#detecting-nuitka-compilation-at-runtime): `sys.frozen` 대신 모듈의 `__compiled__`도 검사하도록 런타임 판별을 확장했습니다.
- [PyInstaller operating modes](https://pyinstaller.org/en/stable/operating-mode.html): 기존 onedir 설치 형태를 유지합니다. 반복 실행마다 onefile 임시 압축 해제를 하는 비교가 아닙니다.
- [Python 3.14 changes](https://docs.python.org/3.14/whatsnew/3.14.html): 이번 실험은 일반 GIL 빌드이며 free-threaded·실험적 JIT를 채택하지 않았습니다. 비교한 버전은 3.14.5로 고정합니다.
